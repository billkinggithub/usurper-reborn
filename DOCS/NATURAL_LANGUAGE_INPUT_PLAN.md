# 自然语言输入：评估与方案

## 一句话结论

**动作与说话：可行，但必须由 AI 理解，规则层会丢信息。**
**问 AI 帮忙：可行，纯只读。**
**让 AI 读写任意系统变量：技术可行，但我不建议让模型直接改。**

---

## 0. 已定的决定（2026-10-25）

| 项 | 决定 |
|---|---|
| 自由动作标记 | `/` 开头 |
| 询问 / 指挥 AI | `@ai` 开头 |
| debug | 折中：AI 只翻译成命令，人确认后由代码执行 |
| v1 动作范围 | **全部**：说话 / 旁白 / 看 / 移动 / 买卖 |

### 规则层被否掉了，原因记在这里

初版方案打算"规则命中就不用 AI"，并假设一句话只对应一个动作。这个假设是错的。玩家会打：

> 我穿上盔甲对他威胁到

一句话里同时有：**穿装备**、**对他说话**、**威胁的语气**。规则层只能抓到其中一个，
其余信息静默丢失——而且丢的往往正是"态度"这种最有价值的部分。

所以：

- **理解必须交给模型**，规则层不做第一道解析
- 模型输出必须能表达**多个同时发生的效果**，而不是一个枚举值
- 说话内容与语气要**忠实传给 NPC**，不能被简化成"你和他说话了"

### 模型可以反问

需求不明确时，模型不猜，而是回一个问题，玩家回答后继续。例如：

```
玩家：/ 给他点颜色看看
AI：你是想威胁他，还是直接动手？
玩家：威胁
AI：（执行：对铁匠摆出威胁姿态，说出一句警告）
```

这才是助手，而不是一个只会匹配正则的解析器。

## 1. 三个需求，风险差距极大

| 需求 | 本质 | 风险 | 建议 |
|---|---|---|---|
| 说"我拍了拍某某肩膀说你好" | 自然语言 → **一个已存在的游戏动作** | 低 | 做，分层实现 |
| 问 AI 求助 | 只读问答 | 低 | 做 |
| 让 AI 读/改系统变量 | **任意状态写入** | **高** | 改造成"调试控制台 + AI 只做翻译" |

第三项是唯一一处，**不该让模型直接执行**。原因不是不信任模型，而是三条工程事实：

1. **不可复现**：模型每次可能给出不同字段名，存档形状随之漂移，出问题无法复现。
2. **失败代价不对称**：读错一个变量无所谓；写错一个字段可能毁掉几十小时的存档。
3. **无法测试**：如果行为由模型决定，就没有可以断言的输入输出。

## 2. 架构：AI 只产出"意图"，执行权永远在代码手里

```
玩家输入「我拍了拍铁匠的肩膀说：老兄，最近生意如何」
        │
        ├─ 规则层（无需 AI）：拍了/说/看/走/买 …… 命中即映射
        │
        └─ 规则没命中且 AI 开着 → 请求模型输出**结构化意图 JSON**
                 { "intent": "GESTURE_AND_TALK", "target": "铁匠", "text": "老兄……" }
                        │
                        ▼
              白名单校验（intent 必须在枚举内，target 必须在场 NPC 里）
                        │
                        ▼
              调用**已有的**游戏方法（InteractWithNPC / 重新渲染地点 / 打印旁白）
```

关键约束：**模型只能在这个枚举里选，不能发明动作**。枚举之外的输出一律丢弃并提示"没听懂"。

### 意图集合（v1）

| 意图 | 效果 | 走哪条已有路径 |
|---|---|---|
| `TALK_TO(target)` | 与在场 NPC 开始对话 | `InteractWithNPC(npc)` |
| `GESTURE(text)` | 纯旁白（拍肩、叹气、举杯） | 打印一行，**不改状态** |
| `LOOK` | 重新描述当前地点 | 现有渲染 |
| `ASK(question)` | 问 AI（见第 4 节） | 只读 |
| `HELP` | 列出能说什么 | 静态文本 |

`MOVE` / `BUY` 这类会改状态的，放到 v2，并且同样只调用已有方法。

## 3. 输入通道：一个标记，36 个地点全生效

现在每个地点自己读菜单键：`GetChoice()` 36 处，直连 `terminal.GetInput(ui.your_choice)` 36 处（分布在 5 个文件）。

方案：任何以 **`/`** 开头的输入都当作自然语言处理，其余照旧走菜单键。这样：

- 不改变现有操作习惯（菜单键照常）
- 不需要改 36 个地点的循环，只需把读取收口到一处
- 地点没实现自由动作时，回答"这里没有可交谈的对象"即可

顺带把 36 处直连改成同一个入口，**这也是后续任何输入层功能的前置条件**。

## 4. 问 AI 求助：只读，且不碰存档

上下文只包含**当前可公开的信息**：地点、在场 NPC 名字、玩家等级/职业/金币、当前菜单选项。
不发送：其他玩家、存档路径、记忆原文、API key。

回答只用于显示，**不参与任何状态计算**。

## 5. debug 控制台：AI 只翻译，人确认，代码执行

这是对"让 AI 改系统变量"的改造，目标是**保住你想要的能力，去掉毁存档的风险**。

### 形态

一个独立控制台，有自己的**固定命令语法**（不是自然语言）：

```
get player.gold
set player.gold 5000
get npc["铁匠"].Aggression
set npc["铁匠"].Aggression 0.9
list npcs
```

玩家可以说自然语言，但流程是：

```
玩家：「把铁匠的好感度调到 90」
  → AI 翻译成：set npc["铁匠"].Relationships["莫里斯"] 90
  → 屏幕显示这条命令 + 「确认执行？(Y/N)」
  → 玩家确认 → 控制台解析 → 类型校验 → 白名单检查 → 执行
```

**模型不接触执行**，它只是把你的话写成一条命令；命令本身可读、可改、可拒绝。

### 三道闸

1. **白名单路径**：只有登记过的对象和字段可读写（player / 在场 NPC / 世界状态里明确列出的项）。不在名单 → 拒绝并列出可用路径。
2. **类型与边界**：`int` 必须能解析，`float` 夹在 0..1，枚举必须合法；失败不写入。
3. **只在单机**：门模式、MUD、中继一律禁用；默认关闭，需在设置里打开，并在首次打开时显示警告。

### 明确不做

- 不做"模型自由拼字段名"，只做"从白名单里选"。
- 不做批量写（`set all npcs.hp 0`），只能逐个。
- 不做无确认写入。

## 6. 一个必须提前处理的安全问题

**提示词注入。** NPC 的名字、对话、物品描述都来自游戏数据，而模组可以改这些数据。如果这些文本进入模型上下文，一段恶意描述就能让模型输出 `set player.gold 999999`。

缓解：

- 模型输出**只允许落在意图枚举/命令白名单**内，任何越界直接丢弃——这是根本防线
- 游戏数据在提示词里**明确标注为数据**，不与指令混排
- debug 的写入永远经过人工确认

## 7. 分阶段

| 阶段 | 内容 | 依赖 AI | 工作量 |
|---|---|---|---|
| 0 | 输入收口：36 处直连并入一个入口，加 `/` 通道 | 否 | 小 |
| 1 | 规则层：TALK_TO / GESTURE / LOOK | **否** | 中 |
| 2 | AI 兜底解析：规则没命中时请求意图 JSON，白名单校验 | 是 | 中 |
| 3 | `ASK` 只读问答 | 是 | 小 |
| 4 | debug 控制台（固定语法 + 人工确认） | 否 | 中 |
| 5 | AI 把自然语言翻译成 debug 命令 | 是 | 小 |

注意 **阶段 1 不需要 AI**：常见说法用规则就能覆盖大半，且完全可测。阶段 2 只是提高覆盖率。

## 8. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 模型输出越界 | 中 | 白名单枚举，越界丢弃 |
| 提示词注入 | 高 | 同上 + 数据/指令分离 + 写入需确认 |
| 玩家感觉"AI 替我玩了" | 中 | 默认关闭；动作仍由玩家发起，AI 只翻译 |
| 延迟 | 中 | 规则层先行，只有未命中才请求；缓存 |
| 存档损坏 | 高 | debug 仅白名单 + 确认 + 单机 |
| 破坏平衡 | 中 | debug 明确标记为作弊，不参与成就/统计 |
