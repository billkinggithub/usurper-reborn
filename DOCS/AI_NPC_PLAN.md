# AI 与 NPC 生动性：评估与方案

## 一句话结论

**技术上可行，而且这个仓库里已经做过一次**——但上一版在 1.0.3 被**全量删除**了。
所以真正的问题不是"能不能接 AI"，而是"这次凭什么不会重蹈覆辙"。

答案是一处设计转向：

> 上一版是**每说一句话就调一次模型**；
> 这一版应该是**每个 NPC 出生时生成一次人设卡，之后永远离线**。

---

## 1. 现状：手里已经有什么

这部分决定成败。没有结构化状态的 LLM 只会输出漂亮的废话。

| 已有资产 | 位置 | 说明 |
|---|---|---|
| 15 维性格 | `Scripts/AI/PersonalityProfile.cs` | 好斗/贪婪/勇气/忠诚/记仇/冲动/社交/野心/可信/谨慎/智力/神秘/耐心/浪漫/温柔，各 0..1 浮点 |
| 关系值 | `RelationshipSystem` | 0..100（0 灵魂伴侣，50 中立，100 憎恨） |
| 记忆 | `Scripts/AI/MemorySystem.cs` | `RecordEvent(MemoryEvent)`，带类型；`MemoryType.KilledMyParent`、`ForgetGrudgesAgainst` 等；每人上限 30 条 |
| 作者写好的台词池 | `Localization/en.json` | `npc_gen` 383 + `npc_dialogue` 580 + `dialogue` 673 + `companion` 260 条 |
| 世界模拟 | `WorldSimulator` | 130 个 NPC 会自己结婚、生子、死亡 |
| 心情/关系偏好/性别认同 | `PersonalityProfile.cs` | 含 `RomanceStyle`、`RelationshipPreference` 等枚举 |

**缺口只有一处**：NPC 没有"自己是谁"的字段。`NPC` 类里有 `Personality`，**没有** `Bio`/`Voice`/`Background`。
所以 130 个 NPC 的差别只体现在数值上——这就是"不像活人"的真正原因。

## 2. 历史：这条路走过，然后被拆了

`DOCS/LLM_CONFIG.md` 开头写着：

> LLM moments were removed in 1.0.3. The game no longer contacts any language model service in any
> mode, reads no `USURPER_LLM_*` variable and has no API key for a server operator to configure.

从 git 里可以完整取回当年的实现（提交 `339ee5ad^`）：

| 文件 | 行数 |
|---|---|
| `LLMMoments.cs`（各类时刻生成器） | 1978 |
| `LLMProvider.cs` | 464 |
| `LLMBudget.cs` | 133 |
| `LLMSettings.cs` | 123 |
| 两个测试文件 | 308 |

删除提交动了 **32 个文件、4,653 行**，还连带删掉了 `llm_usage` 遥测表、平衡面板的标签页和端点、后台健康监控、以及 NPC 上的 11 个缓存字段。

当年的设计其实很克制（`LLMSettings.cs` 注释）：

- 只在线模式，**自建服自带 key**，key 只在服务端
- 走 **OpenAI 兼容端点** → OpenAI / Anthropic / OpenRouter / **本地 Ollama** 都能用
- `USURPER_LLM_DAILY_TOKEN_CAP` 默认 50 万 token（约 $0.50/天）
- 单请求超时 **3000ms**
- **每个调用点都有人写好的回落**，所以在线玩家和离线玩家走的是两套路径

**为什么还是删了**——文档没写动机，但证据指向三点：

1. **成本与运维面太大**：预算、遥测表、健康监控、面板端点，全是为了"在线才有的功能"而生。
2. **只有在线玩家受益**：作者原话 "the feature was built online-only from the start and single player has always run without it"。占多数的单机玩家为它承担了全部复杂度，却一点都不受益。
3. **收益是"台词换个说法"**：它生成的是问候、话题回应、墓志铭、第一印象——**已经被作者池覆盖的东西**。它没有让 NPC 更"记得"你，只是让同样的话换个说辞。

这就是关键教训：**逐句生成，用高运维成本换来了很小的体验增量。**

## 3. 可行性评估

### 技术面：可行，且无未知风险

- provider 抽象、预算、超时、回落、缓存，这套代码仓库历史里就有现成的，可以直接读、直接借。
- 游戏里已经有 `HttpClient` 用法（`BugReportSystem`，10s 超时），加一个可选的 LLM 客户端不属于新领域。
- 本地模型（Ollama / llama.cpp）现在能离线跑，解决了当年"只有在线玩家受益"的硬伤。

### 但有 4 个硬约束必须先设计进去

| 约束 | 现状 | 影响 |
|---|---|---|
| **本地化键体系** | 每句玩家可见文本都是 `Loc.Get(key)`；`LocalizationIntegrityTests` 校验键集、占位符、标点；`HardcodedTextScanner` 是棘轮，禁止 `Scripts/` 里出现硬编码英文 | LLM 生成的句子**没有 key**，无法被校验、无法翻译、无法被棘轮约束 |
| **确定性** | `NPCDialogueGenerator.Rng` 可被测试播种；同一颗种子在所有语言下选出同一组 key | LLM 不确定，测试无法复现 |
| **离线 / BBS door** | 单机、door 模式都可能无网络 | 任何"必须联网"的功能都会把玩家分成两类 |
| **延迟** | 终端逐字输出，一句台词等 3 秒会毁掉节奏 | 不能在玩家等待时同步调用 |

### 一个必须先讲清的判断

用户想要的是"有血有肉"。但**血肉不来自会说话，来自"记得"和"会变"**：

- 他记得你当年救过他 → 这次他主动还你人情
- 你背叛过他 → 他从此只肯说最短的话
- 他昨天刚死了孩子 → 今天打招呼的语气不一样

这些**全部依赖结构化状态和持久化**，LLM 只是在上面加一层"措辞"。反过来做（先接 LLM）只会得到 130 个说话方式雷同、且记不住任何事的角色。

## 4. 设计方案：AI 是"渲染层"，不是"决策层"

### 玩家要能控制的三件事（2026-10-25 补充）

这三条决定了实现形态，先写清楚：

**1. 生成语言跟随语言设置。**
不是固定中文。玩家当前用哪种语言，生成内容就用哪种语言。这意味着缓存必须**按语言分键**：
同一句生成内容，换语言后必须重新生成，不能拿中文的缓存去显示英文界面。人设卡也一样，
卡片里的可读文本与语言绑定；结构化标签（说话长短、执念、关键词）与语言无关，可以共用。

**2. 设置里有独立的 AI 分区。**
新增一节，至少三项：

| 项 | 行为 |
|---|---|
| AI 模式 | 开 / 关，随时可切 |
| API 地址 | 填 OpenAI 兼容端点；填 `http://localhost:11434/v1/chat/completions` 即本地模型 |
| API 密钥 | 掩码输入（`terminal.GetMaskedInput`），屏幕上只显示前 4 位和后 4 位 |

存储位置：**不进存档**。存档会被复制、分享、在不同机器间搬运，密钥不属于角色。
放在 `%APPDATA%\UsurperReloaded\ai.json`，并允许 `USURPER_LLM_ENDPOINT` / `USURPER_LLM_API_KEY` /
`USURPER_LLM_MODEL` 覆盖（自建服可以把密钥留在环境里，不落盘）。

**3. 传统模式与 AI 模式可随时切换。**
切换立即生效，作用于**下一句台词**，不需要重开游戏、不需要重新生成世界。
关掉之后一切回到作者池，已生成的内容不丢（仍在缓存里，再打开就继续用）。
任何时刻失败（无网络、超时、密钥失效、额度用尽）都必须**静默回落到作者池**，
而不是卡住对话或报错打断玩家。

### 核心转向：一次性人设卡

```
旧版（已删）：玩家交互 → 调模型 → 得到一句台词 → 显示
             每次 1 次调用 × 130 NPC × 每小时若干次

新版（建议）：NPC 出生 → 调模型 1 次 → 生成"人设卡" → 存进存档
             之后所有台词 = 人设卡 + 作者模板 + 记忆 本地合成
             全程离线，0 额外调用
```

**收益**：

| | 旧版 | 新人设卡 |
|---|---|---|
| 调用次数 | 每句话 | 每个 NPC 一生 1 次（130 次/存档） |
| 离线可用 | 否 | **是** |
| 一致性 | 弱（每句独立生成） | **强（卡片固定）** |
| 延迟 | 3s/句 | **0（本地合成）** |
| 成本 | 需日预算上限 | 一次性，可忽略 |
| 可测试 | 否 | **是（卡片是数据）** |

人设卡存**结构化字段**，不是大段散文：

```jsonc
{
  "speech": "clipped",          // 说话长短
  "tic": "always_mentions_weather",  // 口头禅/执念
  "regard": "distrustful",      // 对人的默认态度
  "secret": "owes_a_debt",      // 可被记忆系统揭示的钩子
  "keywords": ["铁匠", "旧伤", "北方"]   // 用于话题匹配
}
```

这样它**仍然是可翻译的**：卡片给出的是"标签"，真正的句子由作者模板（`npc_gen.*`）按标签选出来——本地化体系完全不用改。

### 分层

| 层 | 内容 | 依赖网络 | 说明 |
|---|---|---|---|
| **L0** 现状 | 作者池 + 性格加权选择 | 否 | 已经在跑 |
| **L1** 让现有数据真正生效 | 把 15 维性格、关系值、记忆接进台词*选择权重*；补"记忆驱动"的问候 | 否 | **收益最大、风险最低，先做这个** |
| **L2** 人设卡 | NPC 出生时生成一次，存盘；台词按卡片挑选 | 生成时一次 | 让 130 个 NPC 各不相同 |
| **L3** 自由对话 | 玩家自由输入 → 受卡片/记忆/关系约束的回应 | 是（或本地模型） | 只在桌面/在线端，且只对少数 NPC 开 |

### 与本地化的关系

- L0–L2 产生的仍是 `Loc.Get` 句子 → **不破坏任何现有测试**，中文/西语等继续自动成立。
- L3 的自由对话文本**不走 key**。必须：
  1. 在 `LocalizationIntegrityTests` 里加一个明确的"生成内容"豁免类别（机制上参照已有的 `PartialLangs`）；
  2. 在界面上标出这是生成文本；
  3. 把生成内容**排除在存档的权威状态之外**（只存"说过什么"的摘要，不存请求/响应）。

### 记忆归属（关键）

记忆必须**留在游戏里**，用 `MemorySystem.RecordEvent` 存结构化事件。
LLM 只**读**记忆去组织措辞，绝不把记忆写进模型上下文再读回来——否则：
- 不可持久化（重启丢失）
- 不可测试
- 会说谎（模型编造没发生过的事）

## 5. 分阶段计划

### 阶段 0：先回答"要不要"（0.5 天，无代码）

先确认下面第 8 节的 4 个决策点。**如果第 1 个问题答不上来，后面全部不做。**

### 阶段 1：让现有数据生效（3–5 天，不接 AI）

这是**我最推荐先做的一步**，因为它不需要 AI 就能显著提升体验，而且没有运维成本。

- 把 15 维性格接进 `NPCDialogueGenerator` 的选择权重（现在只用了少数几维）
- 把 `MemorySystem` 的事件接进问候语选择：帮过他/打过他/骗过他的 NPC，开场白不同
- 补一组"记忆驱动"的台词键（约 40 条 × 6 语言）
- **验收**：同一个 NPC 在你救过他前后，说的话明显不一样；同一句话不再被 130 个 NPC 原样复用

工作量主要是翻译（40 键 × 6 语言）和权重调参，风险极低。

### 阶段 2：人设卡（5–8 天，可选 AI）

- `NPC` 增加 `VoiceCard` 字段（结构化，可序列化）
- 三档生成方式，**同一套接口**：
  1. 手写（默认，无 AI）：从性格值 + 姓名推导
  2. 本地模型（Ollama）：`USURPER_LLM_ENDPOINT=http://localhost:11434/v1/chat/completions`，离线可用
  3. 云端：同旧版的 OpenAI 兼容端点
- 从历史里取回 `LLMProvider.cs` 作为参考实现（别整份搬，只借 provider 抽象和超时/回落）
- **验收**：断开网络后，已生成的存档里所有 NPC 行为不变；换一台机器读同一存档，行为也不变

### 阶段 3：自由对话（选择性，10+ 天）

- 仅桌面/在线端，默认关闭
- 只对 5 个同伴 + 少数具名 NPC 开启（先验证体验，再谈铺开）
- 需要：提示词模板、输入长度限制、内容过滤、成本上限、明确的"生成内容"标识
- **不建议**在 L3 之前碰这一步

### 阶段 4（暂不建议）：铺到全部 130 NPC

在阶段 2 的验收数据出来之前不要做。130 个 NPC 的自由对话是成本、延迟、一致性问题同时出现的场景。

## 6. 成本

以阶段 2 为例（每个 NPC 生成一次人设卡）：

- 130 个 NPC × 1 次 × 约 400 token ≈ **5 万 token / 存档**
- 云端小模型：约 **$0.01–0.02 / 存档**，一次性
- 本地 Ollama：**0 元**，且离线

对比旧版（逐句生成）：一次两小时的游戏会话，几百次调用，需要日预算上限和遥测表。
**这就是设计差异带来的成本差异，两个数量级。**

## 7. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **重蹈覆辙**：又变成"在线才有的豪华功能" | 高 | 人设卡离线可用；生成是可选步骤，不是运行时依赖 |
| 一致性漂移（同一 NPC 前后矛盾） | 高 | 决策与状态全在代码里；模型只做措辞 |
| 破坏本地化体系 | 高 | L0–L2 仍产出 `Loc` 键；L3 显式豁免并标注 |
| 延迟毁掉终端节奏 | 中 | 运行时 0 调用；生成在"NPC 出生"时后台完成 |
| 成本失控 | 中 | 一次性生成 + 硬性每存档上限 |
| 生成内容不当 | 中 | 只对少数 NPC 开放 + 过滤 + 可关闭 |
| 玩家被分成两类（在线有、离线无） | 中 | 本地模型路径 + 手写卡兜底 |

## 8. 需要拍板的 4 个问题

1. **上次为什么删？** 如果原因是"没人用/运维太重"，那这次必须先用阶段 1 证明"生动性确实能提升"，再谈 AI。
2. **目标平台**：单机为主，还是在线服为主？这决定用本地模型还是服务端 key。
3. **能否接受"生成文本不可翻译"**？能接受的话 L3 才成立；不能接受就只能停在 L2。
4. **愿意为此改存档格式吗**（加 `VoiceCard` 字段）？老存档需要兼容读取。

## 9. 明确不建议的做法

- ❌ **把台词生成整体换成 LLM**：立刻失去本地化、确定性、离线性，并且和 1.0.3 的删除决定直接冲突。
- ❌ **让模型决定 NPC 的行为**（嫁谁、杀谁、是否背叛）：这会破坏 `WorldSimulator` 的可复现性和平衡性。
- ❌ **在存档里存对话历史原文**：会撑爆存档（参考 `MemorySystem` 当年因为 130 NPC 膨胀而把上限从 100 降到 30 的教训）。
- ❌ **先铺 130 个 NPC**：先做 5 个，量出收益再说。
